# Каталог тест-кейсов

Каталог описывает проверки внешнего поведения Atlassian MCP Light. AQA Client подключается к TCP STDIO Bridge; Bridge создаёт отдельный дочерний процесс MCP-сервера и прозрачно проксирует STDIO. AQA не запускает JAR напрямую.

## Общие правила

- ID стабильны и не переиспользуются: `MCP-xxx`, `JIRA-xxx`, `CONF-xxx`, `PROC-xxx`, `DATA-xxx`, `REL-xxx`. Для новых тест-кейсов используются следующие свободные номера соответствующей группы.
- Приоритеты: P0 — критичный для базовой работоспособности; P1 — важная функциональность; P2 — дополнительный негативный/граничный сценарий.
- Типы: Protocol, Process, Integration, Negative, E2E.
- Все тестовые данные должны создаваться в выделенном тестовом окружении.
- В тест-кейсах ниже «валидный запрос» означает запрос, соответствующий фактической JSON Schema инструмента и контракту MCP-сервера.
- Ожидаемые поля и ограничения приведены в [фактическом MCP-контракте](mcp-contract.md); при выполнении теста схема дополнительно сверяется с текущим ответом `tools/list`.

Дополнительные правила протокольных тестов:
- Классический `initialize` принимает версии `2024-11-05` и `2025-11-25`; неизвестная, но непустая версия приводит к выбору `2025-11-25`.
- Повторный `initialize` возвращает `-32600`; `tools/list` и `tools/call` до `notifications/initialized` возвращают `-32001`.
- В stateless-режиме `params._meta` содержит ключи `io.modelcontextprotocol/protocolVersion` и `io.modelcontextprotocol/clientCapabilities`; `clientInfo` необязателен.
- Ошибка параметров метода (например, некорректная metadata) — JSON-RPC `error`; ошибка валидации/выполнения инструмента — `result.isError=true`.

## 2. STDIO Bridge and Session Lifecycle

Каждый Process-тест начинает работу с регистрации заранее привязанного socket endpoint через control channel по контракту bridge-correlation-and-reliability.md; только после успешной регистрации открывается data connection. Подтверждение PID, создания/завершения дочернего процесса и причин завершения выполняется по точным JSONL-событиям Bridge, архивируемым Jenkins. AQA и Bridge находятся в выделенной user-defined Docker network без NAT/proxy, меняющих source IP:port. При отсутствии корреляции lifecycle-тест не может считаться пройденным.

## 8. Что требует уточнения перед автоматизацией

1. При каждом обновлении основного проекта повторно сверять JSON Schema и annotations всех 13 инструментов по `tools/list`.
2. Зафиксировать конкретные обязательные поля `jira_create_issue` для тестового Jira project.
3. Зафиксировать workflow и доступные переходы тестового проекта.
4. Зафиксировать валидные JQL/CQL-запросы и проверить фактическое поведение параметров `limit`.
5. Подтвердить права на создание, чтение и обновление тестовых задач/страниц.
6. Согласовать тестовые project/space, пользователей и процесс последующей ручной/административной очистки. Формат JSONL event log и правила `WRITE_INTENT/WRITE_CONFIRMED/UNKNOWN_OUTCOME` определены в bridge-correlation-and-reliability.md; инструментов удаления в MCP-контракте нет.

До выполнения этих пунктов тест-кейсы являются базовой спецификацией; конкретные payloads должны строиться по фактическим схемам сервера и настройкам тестового tenant.
