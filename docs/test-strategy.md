# Стратегия и план тестирования

## 1. Объект тестирования

**Atlassian MCP Light** — Java 17 MCP-сервер для работы с Jira и Confluence через REST API. Взаимодействие MCP-клиента с сервером выполняется по STDIO; формат сообщений — JSON-RPC 2.0.

Репозиторий объекта тестирования: https://github.com/Solomentcev/atlassian-mcp-light

Сервер состоит из Maven-модулей:

- `atlassian-core` — MCP-протокол, конфигурация, HTTP-клиент и общая инфраструктура;
- `atlassian-jira` — инструменты Jira;
- `atlassian-confluence` — инструменты Confluence;
- `atlassian-mcp-app` — точка входа и сборка приложения.

Исполняемый артефакт по README основного проекта: `atlassian-mcp-app/target/atlassian-mcp-light-1.0-SNAPSHOT.jar`.

## 2. Цель

Проверить, что собранное приложение корректно запускается как отдельный процесс, реализует заявленный MCP/JSON-RPC интерфейс и выполняет операции Jira и Confluence через реальные API.

## 3. Объём тестирования

### Входит в объём

1. Запуск JAR, жизненный цикл процесса и конфигурация.
2. STDIO: stdin, stdout, stderr, несколько последовательных сообщений, UTF-8.
3. JSON-RPC: корректные и некорректные запросы, идентификаторы, ответы и ошибки.
4. MCP: initialize, notifications/initialized, tools/list, tools/call, server discovery — в соответствии с фактически реализованным сервером.
5. Контракт 13 MCP-инструментов: имена, схемы аргументов, результат и ошибки.
6. Интеграция с Jira: чтение, поиск, создание и изменение задач, комментарии, проекты и пользователи.
7. Интеграция с Confluence: чтение страниц и пространств, поиск, создание и обновление страниц.
8. Обработка ошибок авторизации, отсутствующих объектов, недостаточных прав и ошибок API.
9. Allure-отчётность и запуск в Jenkins.

### Не входит в первую версию

- нагрузочное и стресс-тестирование;
- полноценное измерение производительности;
- тестирование UI Jira/Confluence;
- тестирование внутренних Java-классов основного приложения как unit-тестов;
- дублирование всех комбинаций, уже проверяемых unit-тестами основного проекта;
- тестирование сторонних MCP-клиентов как самостоятельных продуктов.

Проверки времени ответа могут использоваться только как sanity-check с широкими техническими таймаутами, но не как performance benchmark.

## 4. Подход и уровни проверок

### 4.1. Black-box process tests

Тестовый проект запускает собранный JAR отдельным процессом через `ProcessBuilder`. Тесты не должны создавать экземпляры классов основного приложения или обращаться к его внутренним сервисам.

Проверяется:
- процесс стартует с корректной конфигурацией;
- процесс не завершается неожиданно до обработки запроса;
- запросы передаются в stdin;
- ответы JSON-RPC читаются из stdout;
- stderr доступен для диагностики;
- посторонний текст и логи не попадают в stdout;
- процесс можно корректно завершить и освободить ресурсы.

### 4.2. MCP/JSON-RPC protocol tests

Проверяются протокольные сообщения и публичный контракт MCP. Эти тесты должны быть максимально независимы от состояния Jira и Confluence, если сценарий не вызывает конкретный инструмент.

### 4.3. Integration tests

Проверяются реальные операции через MCP-интерфейс и реальные Atlassian API. Тесты используют выделенные Jira project и Confluence space, тестовую учётную запись и заранее определённые данные.

### 4.4. End-to-end tests

Небольшой критический набор проходит весь путь: тест → STDIO MCP client → JAR → MCP tool → Atlassian REST API → результат.

## 6. Приоритеты и теги

Приоритет — характеристика важности конкретного тест-кейса. JUnit tags используются для группировки и запуска наборов.

| Tag | Назначение |
|---|---|
| `smoke` | Быстрая проверка работоспособности после сборки |
| `critical` | Минимальный набор критичных пользовательских потоков |
| `integration` | Проверки с реальными Jira/Confluence API |
| `full` | Полный регрессионный набор |

Один тест может иметь несколько тегов, например `critical` и `integration`.

### Предлагаемое распределение

- Smoke: запуск JAR, MCP initialize, tools/list, по одному безопасному read-вызову Jira и Confluence.
- Critical: handshake, корректный вызов инструмента, получение Jira issue, получение Confluence page, создание и чтение тестовых объектов.
- Integration: все тесты, требующие реальных Atlassian API.
- Full: весь набор, включая негативные и граничные сценарии.

## 7. Тестовые окружения и данные

Для интеграционных тестов необходимы:

- отдельный Jira project, предназначенный только для автотестов;
- отдельный Confluence space, предназначенный только для автотестов;
- тестовая Atlassian-учётная запись с минимально необходимыми правами;
- API token;
- заранее известные идентификаторы/ключи тестовых ресурсов;
- возможность создавать, читать, обновлять и удалять тестовые объекты.

Тестовые данные должны быть изолированы от пользовательских и production-данных. Для создаваемых объектов использовать уникальный маркер запуска, например идентификатор тестового запуска и временную метку.

Удаление выполняется только для объектов, созданных текущим тестовым запуском. Если API или права не позволяют безопасно удалить объект, это должно быть явно отражено в сценарии и документации; нельзя удалять объекты по одному лишь совпадению заголовка или имени.

## 8. Конфигурация и секреты

Локально параметры передаются через переменные окружения или локальный файл, исключённый из Git. В Jenkins использовать Credentials.

Минимальные параметры:
- путь к исполняемому JAR основного приложения;
- Jira URL, email и API token;
- Confluence URL, если он отличается от значения по умолчанию;
- ключ тестового Jira project;
- ключ тестового Confluence space;
- таймауты запуска процесса и ожидания ответа.

Не выводить токены, Authorization headers и секреты в Allure, stdout, stderr или Jenkins console log.

## 9. Технический стек тестового проекта

| Компонент | Решение | Назначение |
|---|---|---|
| Язык | Java 17 | Реализация тестов и клиента |
| Сборка | Maven | Зависимости и lifecycle |
| Тестовый фреймворк | JUnit 5 | Тесты, lifecycle, tags |
| Assertions | AssertJ | Проверки результатов |
| JSON | Jackson | Сериализация/десериализация JSON-RPC |
| Отчёты | Allure | Детализация результатов и вложения |
| CI | Jenkins | Сборка и запуск наборов |

Для первой версии реализовать собственный минимальный STDIO MCP client на Java/Jackson. Не подключать MCP SDK без конкретной необходимости. Mockito не использовать: тесты проверяют внешний процесс и реальные ответы.

## 10. Надёжность тестового клиента

Клиент должен:
- запускать процесс с заданными аргументами и environment;
- читать stdout и stderr независимо, чтобы избежать блокировки буферов;
- отправлять JSON-RPC сообщения через stdin;
- сопоставлять ответы с request id;
- не считать уведомление запросом, ожидающим ответ;
- поддерживать несколько запросов в рамках одного процесса;
- иметь отдельные таймауты запуска и ожидания ответа;
- при ошибке сохранять диагностический вывод без секретов;
- корректно закрывать stdin, завершать процесс и освобождать потоки;
- обнаруживать преждевременное завершение процесса.

Не использовать фиксированные `Thread.sleep` для синхронизации. Ожидание строить на чтении ответа, ограниченном таймаутом.

## 11. Allure

Категории:
- Protocol
- Jira
- Confluence
- Negative
- Integration

Каждый тест должен иметь стабильный ID и понятное имя. В отчёт добавлять:
- отправленное JSON-RPC сообщение с маскированием секретов;
- полученный ответ;
- stderr при ошибке;
- exit code и состояние процесса, если применимо;
- идентификаторы созданных тестовых объектов.

Не прикладывать токены, заголовки авторизации и полные секретные конфигурации.

## 12. Jenkins pipeline

Последовательность:
1. Checkout тестового репозитория.
2. Подготовка JDK 17.
3. Получение/сборка JAR основного проекта.
4. Maven build тестового проекта.
5. Smoke suite.
6. Critical suite.
7. Integration/full suite — по выбранному режиму запуска.
8. Публикация Allure report.
9. Архивация логов и диагностических артефактов.

GitHub Actions не используется. Секреты интеграционного окружения хранить в Jenkins Credentials.

На первом этапе достаточно ручного запуска Jenkins job. Автоматический триггер по изменениям основного репозитория можно добавить после стабилизации процесса сборки и передачи артефакта.

## 13. Критерии готовности первой версии

- [ ] Тестовый проект собирается на JDK 17.
- [ ] JAR основного приложения запускается как отдельный процесс.
- [ ] STDIO обмен работает без примеси логов в stdout.
- [ ] MCP handshake и tools/list проверяются автоматически.
- [ ] Все 13 инструментов представлены в матрице покрытия.
- [ ] Есть критические интеграционные проверки Jira и Confluence.
- [ ] Тестовые данные изолированы и имеют безопасную очистку.
- [ ] Секреты не попадают в репозиторий и отчёты.
- [ ] Allure формирует читаемый отчёт.
- [ ] Jenkins выполняет сборку и выбранные наборы тестов.

## 14. Известные ограничения и уточнения

- Версию MCP-протокола в тестах не фиксировать произвольной константой: сверять с поддерживаемой версией и фактическим ответом сервера.
- Точный формат успешных и ошибочных результатов инструментов сверять с их текущей реализацией и публичным контрактом.
- Доступность отдельных негативных сценариев зависит от прав тестовой учётной записи и возможностей Atlassian Cloud.
- Для переходов Jira нужен тестовый workflow, в котором заранее известны доступные статусы и переходы.
- Для поиска и пагинации нужны тестовые наборы, размер которых позволяет воспроизвести несколько страниц результатов.
