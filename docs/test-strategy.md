# Стратегия и план тестирования

## 1. Объект тестирования

**Atlassian MCP Light** — Java 17 MCP-сервер для работы с Jira и Confluence через REST API. Основной транспорт — STDIO; сообщения передаются построчно в UTF-8 как JSON-RPC 2.0. В реализации присутствуют классический MCP lifecycle (версии 2024-11-05 и 2025-11-25) и отдельный stateless-режим (2026-07-28).

Репозиторий объекта тестирования: https://github.com/Solomentcev/atlassian-mcp-light

Сервер состоит из Maven-модулей:

- `atlassian-core` — MCP-протокол, конфигурация, HTTP-клиент и общая инфраструктура;
- `atlassian-jira` — инструменты Jira;
- `atlassian-confluence` — инструменты Confluence;
- `atlassian-mcp-app` — точка входа и сборка приложения.

Исполняемый артефакт по README основного проекта: `atlassian-mcp-app/target/atlassian-mcp-light-1.0-SNAPSHOT.jar`.

## 2. Цель

Проверить внешний контракт Atlassian MCP Light через TCP-подключение к STDIO Bridge: жизненный цикл изолированных сессий, MCP/JSON-RPC интерфейс и операции Jira/Confluence через реальные API.

## 3. Объём тестирования

### Входит в объём

1. Доступность Bridge и жизненный цикл TCP-соединения.
2. Запуск и завершение дочернего MCP-процесса на каждое соединение Bridge.
3. Прозрачная передача STDIO: stdin, stdout, stderr, несколько последовательных сообщений, UTF-8.
4. JSON-RPC: корректные и некорректные запросы, идентификаторы, ответы и ошибки.
5. MCP: классический initialize/notifications/initialized и stateless server/discover; tools/list и tools/call в обоих режимах.
6. Контракт 13 MCP-инструментов: имена, схемы аргументов, результат и ошибки.
7. Интеграция с Jira: чтение, поиск, создание и изменение задач, комментарии, проекты и пользователи.
8. Интеграция с Confluence: чтение страниц и пространств, поиск, создание и обновление страниц.
9. Обработка ошибок авторизации, отсутствующих объектов, недостаточных прав и ошибок API.
10. Allure-отчётность и запуск в Jenkins.

### Не входит в первую версию

- нагрузочное и стресс-тестирование;
- полноценное измерение производительности;
- тестирование UI Jira/Confluence;
- тестирование внутренних Java-классов основного приложения как unit-тестов;
- дублирование всех комбинаций, уже проверяемых unit-тестами основного проекта;
- тестирование сторонних MCP-клиентов как самостоятельных продуктов.

Проверки времени ответа могут использоваться только как sanity-check с широкими техническими таймаутами, но не как performance benchmark.

## 4. Подход и уровни проверок

### 4.1. Black-box process tests

AQA-контейнер не запускает JAR основного приложения через `ProcessBuilder`: JAR работает в отдельном MCP Server container. Тестовый клиент устанавливает TCP-соединение с STDIO Bridge по внутренней Docker network.

На каждое принятое Bridge-соединение создаётся отдельный дочерний процесс MCP-сервера. Bridge прозрачно передаёт байты TCP → stdin и stdout → TCP; stderr направляется в диагностический лог контейнера. Bridge не разбирает JSON-RPC и не меняет MCP-сообщения.

Проверяется:
- Bridge доступен только внутри тестовой Docker network;
- при подключении создаётся отдельная MCP-сессия и дочерний процесс;
- запросы проходят через Bridge без изменения framing и содержимого;
- ответы передаются клиенту, диагностические логи не попадают в MCP-поток;
- несколько запросов последовательно обрабатываются в одной сессии;
- независимые соединения не смешивают сообщения и состояния;
- закрытие/аварийный разрыв соединения приводит к завершению дочернего процесса;
- таймауты и ошибки запуска/завершения обрабатываются контролируемо.

Проверки MCP-контракта остаются black-box: AQA взаимодействует с сервером только через TCP endpoint Bridge и JSON-RPC поток. Внутренние классы MCP-сервера не являются объектом тестирования. Для проверок жизненного цикла дочерних процессов используется отдельная наблюдаемость Bridge: структурированные диагностические записи, собираемые Jenkins. Эти записи не передаются по TCP в MCP-поток и не меняют протокол.

Корреляция выполняется через отдельный Bridge control channel по контракту [bridge-correlation-and-reliability.md](bridge-correlation-and-reliability.md). AQA заранее привязывает socket, регистрирует endpoint, затем подключает тот же socket к data port. Предполагается выделенная user-defined Docker network только между AQA и MCP Server без NAT/proxy, меняющих source IP:port. Процессы внутри AQA container считаются доверенными; endpoint mapping не защищает от скомпрометированного процесса внутри контейнера. Bridge атомарно связывает фактический remote IP:port с регистрацией/clientSessionId и connectionId; PID появляется после успешного запуска. При отсутствии однозначного сопоставления Process-тест падает; подбор по времени/PID запрещён.

### 4.2. MCP/JSON-RPC protocol tests

Проверяются протокольные сообщения и публичный контракт MCP. Эти тесты должны быть максимально независимы от состояния Jira и Confluence, если сценарий не вызывает конкретный инструмент.

### 4.3. Integration tests

Проверяются реальные операции через MCP-интерфейс и реальные Atlassian API. Тесты используют выделенные Jira project и Confluence space, тестовую учётную запись и заранее определённые данные.

### 4.4. End-to-end tests

Небольшой критический набор проходит весь путь: тест → MCP Client → TCP Bridge → STDIO дочернего MCP-процесса → MCP tool → Atlassian REST API → результат.

## 5. Фактический MCP-контракт

Контракт сверён с исходным кодом основного проекта, ветка master. Подробные поля JSON-RPC, metadata, коды ошибок, версии протокола, схемы параметров и annotations вынесены в [Фактический MCP/JSON-RPC контракт](mcp-contract.md).

Обязательные протокольные проверки включают оба режима:
- классический: initialize → notifications/initialized → tools/list/tools/call;
- stateless: server/discover, затем tools/list/tools/call с per-request params._meta и версией 2026-07-28.

Stateless-запросы не требуют initialize и не переводят классическое состояние процесса в READY. Ошибки вызова инструмента (result.isError=true) необходимо отличать от JSON-RPC error.

## 7. Приоритеты и теги

Приоритет — характеристика важности конкретного тест-кейса. JUnit tags используются для группировки и запуска наборов.

| Tag | Назначение |
|---|---|
| `smoke` | Быстрая проверка работоспособности после сборки |
| `critical` | Минимальный набор критичных пользовательских потоков |
| `integration` | Проверки с реальными Jira/Confluence API |
| `full` | Полный регрессионный набор |

Один тест может иметь несколько тегов, например `critical` и `integration`.

### Предлагаемое распределение

- Smoke: подключение к Bridge, создание MCP-сессии, проверка поддерживаемого lifecycle, tools/list и по одному безопасному read-вызову Jira и Confluence.
- Critical: handshake, корректный вызов инструмента, получение Jira issue, получение Confluence page, создание и чтение тестовых объектов.
- Integration: все тесты, требующие реальных Atlassian API.
- Full: весь набор, включая негативные и граничные сценарии.

## 8. Тестовые окружения и данные

Для интеграционных тестов необходимы:

- отдельный Jira project, предназначенный только для автотестов;
- отдельный Confluence space, предназначенный только для автотестов;
- тестовая Atlassian-учётная запись с минимально необходимыми правами;
- API token;
- заранее известные идентификаторы/ключи тестовых ресурсов;
- права на создание, чтение и обновление тестовых объектов.

Тестовые данные должны быть изолированы от пользовательских и production-данных. Каждый прогон получает уникальный AQA_RUN_ID, а каждый тест — собственный стабильный testId. Каждая MCP-сессия получает clientSessionId; Bridge присваивает connectionId, а после старта процесса фиксируется PID. Маркер включается в создаваемые имена/содержимое, а ID созданных объектов регистрируются сразу после успешного создания.

**Ограничение фактического MCP-контракта:** среди 13 инструментов нет операций удаления Jira-задач и Confluence-страниц. Поэтому первая версия AQA не должна обещать автоматическое удаление объектов через MCP и не должна обходить проверяемый интерфейс прямыми вызовами Atlassian API.

В первой версии `TestDataManager` ведёт append-only JSONL event log. До отправки write-запроса сохраняется `WRITE_INTENT` с operationId, `AQA_RUN_ID`, `testId`, инструментом и уникальным marker; после подтверждения — `WRITE_CONFIRMED` с ID объекта; при доказанном отказе — `WRITE_REJECTED`. Незавершённый intent после потери ответа/аварии восстанавливается как `UNKNOWN_OUTCOME`. Каждая строка синхронно сбрасывается на диск; это не транзакция с Atlassian API, но предотвращает потерю самого факта намерения выполнить запись. Реестр и маркеры позволяют безопасно идентифицировать данные для последующей ручной очистки. Удаление через отдельный административный инструмент/API может быть добавлено позднее как самостоятельная операция с явным allowlist и отдельными правами; оно не входит в первую версию AQA.

Нельзя удалять или изменять заранее существовавшие объекты только по совпадению имени, заголовка или маркера.


## 9. Конфигурация и секреты

Локально параметры передаются через переменные окружения или локальный файл, исключённый из Git. В Jenkins использовать Credentials.

Минимальные параметры AQA:
- `MCP_BRIDGE_CONTROL_HOST` и `MCP_BRIDGE_CONTROL_PORT`;
- `MCP_BRIDGE_DATA_HOST` и `MCP_BRIDGE_DATA_PORT`;
- `AQA_REGISTRATION_TTL_MS`, `CONTROL_CONNECT_TIMEOUT_MS`, `CONTROL_RESPONSE_TIMEOUT_MS`, `DATA_CONNECT_TIMEOUT_MS`;
- таймаут ожидания MCP-ответа, запуска процесса и закрытия сессии;
- `AQA_PARALLELISM`;
- ключ тестового Jira project;
- ключ тестового Confluence space;
- уникальный `AQA_RUN_ID`.

Путь к JAR, параметры запуска Java-процесса и конфигурация Jira/Confluence основного приложения не передаются AQA Client. JAR и секреты Atlassian доступны только MCP Server container. Jenkins выбирает ревизию основного проекта, передаёт JAR в MCP Server container и фиксирует commit SHA в параметрах/метаданных прогона.


Не выводить токены, Authorization headers и секреты в Allure, stdout, stderr или Jenkins console log.

## 11. Надёжность тестового клиента

`McpSessionManager` совместно с `BridgeControlClient` должны:
- создавать socket и привязывать его к локальному IP/port до подключения;
- регистрировать endpoint через `MCP_BRIDGE_CONTROL_HOST:MCP_BRIDGE_CONTROL_PORT`;
- подключать к `MCP_BRIDGE_DATA_HOST:MCP_BRIDGE_DATA_PORT` тот же socket, который был зарегистрирован;
- получать status/diagnostics и отменять неиспользованную регистрацию через control channel;
- использовать отдельные `CONTROL_CONNECT_TIMEOUT_MS` и `CONTROL_RESPONSE_TIMEOUT_MS`; таймаут регистрации не должен приводить к автоматическому повтору команды без проверки состояния.

`AQA_REGISTRATION_TTL_MS` задаёт TTL только для незапущенной регистрации в состоянии REGISTERED. После data binding Bridge отменяет registration TTL; активная MCP-сессия управляется `IDLE_SESSION_TIMEOUT_MS` и `PROCESS_STOP_TIMEOUT_MS`.

`McpClient` должен:
- передавать MCP/JSON-RPC сообщения по TCP как UTF-8 JSON Lines без собственного дополнительного framing;
- читать ответы из TCP-потока и сопоставлять их с `request id`;
- не ожидать ответ на notification;
- поддерживать несколько последовательных запросов в рамках одного TCP-соединения;
- поддерживать отдельные классический и stateless режимы согласно `mcp-contract.md`;
- различать JSON-RPC error и MCP tool result с `isError=true`;
- использовать ограниченный таймаут ожидания MCP-ответа и закрытия data-соединения;
- при ошибке сохранять диагностические данные без секретов;
- корректно закрывать TCP-соединение и освобождать клиентские ресурсы;
- обнаруживать преждевременное закрытие соединения и неполный ответ.

MCP Client не запускает JAR, не использует `ProcessBuilder`, не читает stdout/stderr дочернего процесса и не завершает его напрямую. Эти обязанности принадлежат STDIO Bridge. Сведения о запуске/завершении процесса проверяются отдельно по структурированным логам Bridge, которые сохраняются Jenkins и коррелируются по идентификатору соединения.


Не использовать фиксированные Thread.sleep для синхронизации. Ожидание строить на чтении ответа, ограниченном таймаутом.

### 11.1. Параллельность

Параллелятся только JUnit-классы. Каждый класс получает отдельную MCP-сессию и отдельный дочерний процесс; методы внутри класса выполняются последовательно. AQA_PARALLELISM не может превышать MAX_ACTIVE_SESSIONS Bridge. Параллельное выполнение методов одного класса и совместное использование сессии конкурентными тестами запрещены.

### 11.2. Повторные запросы и неопределённый результат

Автоматический retry допускается для read-only вызовов только при ошибке до отправки запроса. Для jira_create_issue, jira_add_comment, jira_transition, confluence_create_page и confluence_update_page автоматические повторы запрещены. Если write-запрос мог дойти до сервера, но ответ потерян, результат фиксируется как `UNKNOWN_OUTCOME`. Для `jira_create_issue` и `confluence_create_page` выполняется сверка по уникальному маркеру/ID; повтор создания разрешается только после доказательства отсутствия объекта. `jira_add_comment`, `jira_transition` и `confluence_update_page` автоматически не повторяются. Для `jira_add_comment` нет инструмента чтения комментариев через MCP, поэтому потерянный ответ остаётся `UNKNOWN_OUTCOME` и требует ручной сверки без повтора.

Confluence update проверяет версию страницы. При конфликте версия перечитывается для диагностики, но автоматическая перезапись не выполняется.

### 11.3. Диагностика

Bridge пишет JSONL-события с обязательными `timestamp`, `sequence` и `event`; runId/testId/clientSessionId/registrationId добавляются после регистрации, connectionId/remote endpoint — после binding, PID — после старта процесса. Для отклонённого незарегистрированного соединения используется connectionAttemptId и фактический remote endpoint. Jenkins архивирует полный лог; Allure прикладывает только записи точно сопоставленной сессии. Отсутствие обязательных событий/корреляции является ошибкой process-теста. sessionToken, секреты, Authorization headers и полный environment dump запрещены.

## 12. Allure

Категории:
- Protocol
- Process
- Configuration
- Jira
- Confluence
- Negative
- Integration
- Test Data

Каждый тест должен иметь стабильный ID и понятное имя. В отчёт добавлять:
- отправленное JSON-RPC сообщение с маскированием секретов;
- полученный ответ;
- диагностические записи Bridge по `clientSessionId`/`connectionId`; отсутствие обязательной записи корреляции является ошибкой lifecycle-теста;
- exit code дочернего процесса из логов Bridge, если применимо;
- идентификаторы созданных тестовых объектов.

Не прикладывать токены, заголовки авторизации и полные секретные конфигурации.

## 13. Jenkins pipeline

Последовательность:
1. Checkout AQA-репозитория и выбранной ревизии основного проекта.
2. Сборка JAR основного проекта в Build container.
3. Передача JAR в MCP Server container и запуск STDIO Bridge.
4. Сборка AQA-образа.
5. Запуск выбранного набора тестов в AQA container через внутреннюю Docker network.
6. Публикация JUnit XML и Allure report.
7. Сохранение диагностических логов Bridge и реестра созданных Atlassian-объектов.
8. Cleanup контейнеров, сети и временных томов. Atlassian-объекты в первой версии не удаляются.

Build container и MCP Server используют общий именованный Docker volume `mcp-artifact`: Build записывает `/artifacts/atlassian-mcp-light.jar`, MCP Server монтирует volume read-only. AQA container не подключается к этому volume. Максимальная длительность Jenkins Pipeline — 12 часов; TTL orphan-ресурсов — 24 часа. Host-level janitor запускается не реже одного раза в час и удаляет только ресурсы с `managed-by=atlassian-mcp-light-autotests`, `aqa-run-id` и истёкшим `expires-at` (UTC Unix epoch seconds).

Сбор артефактов и cleanup должны выполняться в Jenkins post/always при доступных агенте, workspace и Docker daemon. Потеря агента/host не может быть обработана самим Pipeline; orphan-ресурсы требуют отдельной host-level процедуры.

GitHub Actions не используется. Секреты интеграционного окружения хранить в Jenkins Credentials.

На первом этапе достаточно ручного запуска Jenkins job. Автоматический триггер по изменениям основного репозитория можно добавить после стабилизации процесса сборки и передачи артефакта.

## 14. Критерии готовности первой версии

- [ ] Тестовый проект собирается на JDK 17.
- [ ] JAR собирается в Build container и передаётся через именованный volume `mcp-artifact`, смонтированный read-only в MCP Server container.
- [ ] Bridge создаёт отдельный дочерний процесс на каждое клиентское соединение, а его lifecycle подтверждается структурированными диагностическими логами.
- [ ] Корреляция AQA_RUN_ID/testId/clientSessionId/connectionId/PID детерминирована через отдельный control channel.
- [ ] Параллельность ограничена числом Bridge sessions; один тестовый класс использует одну сессию, методы выполняются последовательно.
- [ ] Нет автоматических повторов неидемпотентных write-операций; неопределённые исходы сверяются.
- [ ] Реестр объектов сохраняется инкрементально и архивируется при любом исходе Pipeline.
- [ ] Jenkins собирает артефакты и выполняет cleanup при успехе, падении тестов и сбое промежуточного этапа, пока доступны агент и Docker daemon; потеря агента покрывается host-level janitor, который удаляет только помеченные ресурсы после TTL 24 часа.
- [ ] AQA Client подключается к Bridge по внутренней Docker network.
- [ ] Передача STDIO через Bridge работает без примеси логов в MCP-поток.
- [ ] Классический MCP handshake и stateless server/discover проверяются автоматически.
- [ ] Stateless tools/list и tools/call работают без initialize.
- [ ] Проверяются версии протокола, обязательные metadata и ошибки обоих режимов.
- [ ] JSON-RPC error и MCP tool result с isError=true различаются.
- [ ] Все 13 инструментов представлены в матрице покрытия.
- [ ] Есть критические интеграционные проверки Jira и Confluence.
- [ ] Тестовые данные изолированы; реестр созданных объектов сохраняется для последующей безопасной очистки.
- [ ] Секреты не попадают в репозиторий и отчёты.
- [ ] Allure формирует читаемый отчёт.
- [ ] Jenkins выполняет сборку и выбранные наборы тестов, сохраняет диагностические логи Bridge и реестр тестовых объектов.

## 15. Известные ограничения и уточнения

- Контракт классического и stateless MCP-режимов сверён с исходным кодом ветки master и описан в [mcp-contract.md](mcp-contract.md). Контрольный runtime-прогон ещё предстоит выполнить при реализации AQA-клиента.
- Доступность отдельных негативных сценариев зависит от прав тестовой учётной записи и возможностей Atlassian Cloud.
- Для переходов Jira нужен тестовый workflow, в котором заранее известны доступные статусы и переходы.
- Для `jira_search`, `confluence_search` и `confluence_list_spaces` контракт предоставляет параметр `limit`, но не механизм перехода на следующую страницу. Проверяются границы и значения `limit`; полноценная пагинация требует расширения контракта.
- MCP-контракт не предоставляет инструмент чтения комментариев Jira. Поэтому JIRA-013 проверяет успешный MCP-ответ `jira_add_comment`, но не обещает независимую проверку тела созданного комментария через MCP.
