# Техническая спецификация AQA-фреймворка

## 1. Назначение

Документ описывает архитектуру и техническую реализацию внешних автотестов Atlassian MCP Light. Тестовый проект запускает собранное приложение как самостоятельный процесс и взаимодействует с ним через публичный MCP STDIO-интерфейс.

Основной принцип — black-box testing. Тесты не должны импортировать классы основного приложения, обращаться к его внутренним сервисам или подменять HTTP-клиент основного приложения.

## 4. Зависимости

Для первой версии использовать только необходимые библиотеки:

| Зависимость | Назначение |
|---|---|
| JUnit Jupiter | Тестовый фреймворк, lifecycle и теги |
| AssertJ | Проверки результатов |
| Jackson Databind | Работа с JSON |
| Allure JUnit 5 | Отчётность Allure |
| Maven Surefire | Запуск тестов Maven |

Версии библиотек фиксировать в `pom.xml` и при необходимости централизовать в properties или dependencyManagement. Не использовать диапазоны версий и SNAPSHOT-зависимости сторонних библиотек.

Не добавлять на старте:
- MCP SDK — клиент первой версии реализуется поверх Jackson и STDIO;
- Mockito — тестируется внешний процесс, а не внутренние классы;
- Selenium/Selenide — UI не входит в объём;
- REST Assured — вызовы Jira/Confluence выполняются через MCP-инструменты, а не напрямую из тестов;
- отдельный DI-контейнер — для текущей структуры он не требуется.

## 5. Конфигурация

Конфигурация загружается один раз при старте тестового набора. При отсутствии обязательных параметров тесты должны завершаться понятной ошибкой конфигурации до запуска процесса.

Предлагаемые переменные окружения:

| Переменная | Обязательность | Назначение |
|---|---:|---|
| `MCP_SERVER_JAR` | Да | Путь к JAR основного приложения |
| `MCP_JAVA_EXECUTABLE` | Нет | Путь к Java executable; по умолчанию `java` из PATH |
| `MCP_STARTUP_TIMEOUT_SECONDS` | Нет | Таймаут запуска процесса |
| `MCP_RESPONSE_TIMEOUT_SECONDS` | Нет | Таймаут ожидания ответа |
| `MCP_SHUTDOWN_TIMEOUT_SECONDS` | Нет | Таймаут штатного завершения |
| `ATLASSIAN_BASE_URL` | Для интеграционных тестов | Базовый URL Atlassian |
| `ATLASSIAN_EMAIL` | Для интеграционных тестов | Email тестовой учётной записи |
| `ATLASSIAN_API_TOKEN` | Для интеграционных тестов | API token |
| `JIRA_TEST_PROJECT_KEY` | Для Jira-тестов | Ключ тестового Jira project |
| `CONFLUENCE_TEST_SPACE_KEY` | Для Confluence-тестов | Ключ тестового Confluence space |

Если Jira и Confluence используют разные base URL, конфигурацию необходимо разделить на `JIRA_BASE_URL` и `CONFLUENCE_BASE_URL`. Не предполагать, что оба сервиса обязательно размещены на одном адресе.

Секреты:
- не хранить в Git;
- не помещать в тестовые ресурсы;
- не выводить в логи, сообщения исключений и Allure;
- локально передавать через переменные окружения;
- в Jenkins получать из Credentials.

## 6. Управление процессом сервера

### 6.1. Запуск

Процесс запускается через `ProcessBuilder`:

```bash
java -jar <path-to-jar>
```

Требования:
1. Проверить, что файл JAR существует и доступен для чтения.
2. Запустить процесс с явно заданным рабочим каталогом и окружением.
3. Не объединять stderr со stdout.
4. Сразу запустить независимых читателей stdout и stderr.
5. Зафиксировать время запуска и состояние процесса.
6. Проверить, что процесс не завершился с ошибкой до первой протокольной операции.

Нельзя считать сам факт создания объекта `Process` доказательством готовности сервера. Готовность подтверждается успешным обменом по MCP.

### 6.2. Чтение потоков

stdout и stderr читаются параллельно. Если читать только один поток, второй может заполнить системный буфер и заблокировать процесс.

- stdout — только протокольные сообщения;
- stderr — диагностические сообщения приложения;
- строки stdout передаются MCP-клиенту без предварительной модификации;
- stderr сохраняется в ограниченном буфере для диагностики;
- при сохранении логов необходимо маскировать чувствительные данные.

Не использовать один общий reader для обоих потоков и не направлять stderr в stdout.

### 6.3. Завершение

При завершении тестов:
1. Закрыть stdin процесса.
2. Дождаться завершения в пределах настроенного таймаута.
3. Если процесс не завершился, вызвать принудительное завершение.
4. Дождаться фактического завершения.
5. Закрыть потоки и освободить ресурсы.
6. Сохранить exit code и stderr при аварийном завершении.

Завершение должно выполняться в `@AfterAll` или через единый lifecycle-компонент, чтобы не оставлять дочерние процессы после тестов.

## 7. Реализация MCP STDIO-клиента

### 7.1. Формат обмена

Клиент отправляет JSON-RPC 2.0 сообщения в stdin сервера и читает ответы из stdout. Каждое сообщение передаётся отдельной строкой UTF-8.

Запрос имеет стандартные поля:
- `jsonrpc` со значением `2.0`;
- `id` — уникальный идентификатор запроса;
- `method`;
- `params`, если они предусмотрены методом.

Клиент должен генерировать уникальные request id в пределах процесса. Ответ сопоставляется с запросом по id, а не по порядку или содержимому результата.

### 7.2. Методы для базовой сессии

Последовательность базовой MCP-сессии:

1. `initialize` — запрос инициализации;
2. получение ответа и проверка результата;
3. `notifications/initialized` — уведомление без request id;
4. `tools/list` — получение списка инструментов;
5. `tools/call` — вызов выбранного инструмента.

Текущая реализация основного приложения также содержит современный stateless/modern путь с методами `server/discover`, `tools/list` и `tools/call`. В тестах необходимо проверять тот вариант протокола, который реально используется выбранным клиентским handshake. Не смешивать сообщения разных режимов в одной сессии без отдельного сценария.

### 7.3. Ответы и ошибки

Клиент должен различать:
- успешный JSON-RPC response с `result`;
- JSON-RPC error с объектом `error`;
- MCP tool result с `isError: true`;
- notification, на которое ответ не ожидается.

В текущей реализации основного приложения ошибки вызова инструмента формируются как успешный JSON-RPC response, внутри результата которого находится `isError: true` и текстовый элемент `content`. Не трактовать такую ошибку как JSON-RPC error.

Неизвестный JSON-RPC метод, ошибки структуры запроса и ошибки параметров протокола проверяются отдельно от ошибок выполнения MCP-инструмента.

### 7.4. Таймауты

Ожидание ответа ограничивается таймаутом. Таймаут не должен реализовываться фиксированным `Thread.sleep`.

При истечении таймаута:
- тест завершается с понятным сообщением;
- прикладываются отправленный запрос, доступный stderr и состояние процесса;
- клиент не должен бесконечно блокироваться на чтении stdout.

Для первой версии достаточно синхронной модели запрос-ответ, если тесты не требуют параллельных запросов. Не добавлять сложный multiplexing без реального сценария.

### 7.5. Устойчивость к некорректным сообщениям

Тестовый клиент не должен самопроизвольно отправлять malformed JSON в обычном методе `call`. Для негативных протокольных тестов предусмотреть отдельный низкоуровневый метод отправки raw line, чтобы не смешивать некорректные данные с типизированным API клиента.

## 8. API тестового клиента

Предлагаемый минимальный публичный интерфейс:

```java
public interface McpStdioClient extends AutoCloseable {

    JsonNode request(String method, JsonNode params);

    JsonNode callTool(String toolName, ObjectNode arguments);

    void notify(String method, JsonNode params);

    @Override
    void close();
}
```

Это ориентир API, а не требование создавать отдельный интерфейс и реализацию, если на первом этапе достаточно одного класса. Внутри клиента необходимо обеспечить:
- генерацию request id;
- сериализацию JSON;
- запись одной строки в stdin;
- чтение соответствующего ответа;
- проверку JSON-RPC envelope;
- разбор result/error;
- обработку таймаутов и завершения процесса.

Для `callTool` проверять `result.isError` отдельно от наличия JSON-RPC `error`.

## 9. Тестовые слои и JUnit lifecycle

Рекомендуемые базовые классы:
- `McpProcessTestBase` — запуск JAR и создание MCP-клиента для protocol/process тестов;
- `AtlassianIntegrationTestBase` — общая конфигурация интеграционного окружения и тестового контекста.

Не запускать отдельный серверный процесс для каждого метода теста без необходимости. Для протокольного набора допустима общая сессия на класс, если тесты не влияют друг на друга. Сценарии, проверяющие состояние процесса или некорректный обмен, должны получать изолированный процесс.

Интеграционные тесты должны явно зависеть от наличия тестового окружения. Если параметры Atlassian отсутствуют, их следует пропускать с понятной причиной либо запускать только соответствующие наборы по Maven profile. Не допускать тихого пропуска всех интеграционных проверок в CI.

Теги JUnit:
- `smoke`;
- `critical`;
- `integration`;
- `full`.

Теги обозначают наборы запуска и могут комбинироваться. Конкретные комбинации и фильтры закрепить в Maven Surefire/Jenkins.

## 10. Тестовые данные

### 10.1. Идентификатор запуска

Каждый запуск получает уникальный `testRunId`. Он используется в заголовках, описаниях и содержимом создаваемых объектов, если соответствующее поле поддерживается API.

Пример маркера:

```text
mcp-autotest-<testRunId>
```

### 10.2. Изоляция

- Использовать только выделенные тестовые Jira project и Confluence space.
- Не изменять заранее существующие пользовательские объекты.
- Перед изменением проверять, что объект принадлежит тестовому набору.
- Сохранять ID созданных объектов сразу после успешного создания.
- Удалять только объекты, ID которых записаны текущим запуском.
- Очистку выполнять в `finally`/lifecycle cleanup, не полагаясь только на успешное завершение теста.

### 10.3. Повторяемость

Тесты должны быть повторяемыми:
- входные данные фиксированы или генерируются детерминированно;
- уникальные маркеры предотвращают коллизии параллельных запусков;
- тесты не зависят от порядка выполнения;
- для workflow Jira явно задано ожидаемое начальное состояние;
- тесты пагинации используют подготовленный объём данных, а не случайное содержимое tenant.

Если cleanup не удался, тест должен оставить диагностическую запись с ID объекта, но не скрывать исходную ошибку теста.

## 11. Allure и диагностика

Для каждого теста указывать:
- стабильный ID тест-кейса;
- понятное имя;
- Epic/Feature или соответствующую функциональную область;
- тип проверки;
- шаги MCP-взаимодействия.

Полезные вложения:
- JSON-RPC request;
- JSON-RPC response;
- stdout/stderr при ошибке;
- exit code процесса;
- ID созданных тестовых объектов;
- сведения об окружении без секретов.

Категории ошибок:
- Protocol;
- Process;
- Jira;
- Confluence;
- Test Data;
- Configuration.

Не прикладывать API token, Authorization header, пароль или полный environment dump. Перед добавлением JSON в Allure выполнять маскирование чувствительных полей.

## 13. Jenkins pipeline

Этапы:
1. Получить исходный код AQA-проекта.
2. Подготовить JDK 17 и Maven.
3. Получить исходный код основного проекта и собрать JAR либо получить заранее собранный артефакт.
4. Передать путь к JAR через `MCP_SERVER_JAR`.
5. Запустить smoke-набор.
6. При успешном smoke выполнить critical и выбранные integration/full наборы.
7. Опубликовать Allure Report.
8. Архивировать результаты и диагностические логи.

Для интеграционного этапа использовать Jenkins Credentials и выделенные тестовые ресурсы. Не передавать секреты через параметры командной строки, если они могут отобразиться в process list или логах.

GitHub Actions не используется. На первом этапе Jenkins запускается вручную; автоматическую связь сборок двух репозиториев добавить после стабилизации передачи артефакта.

## 14. Порядок реализации

### Этап 1. Основа проекта
- создать Maven-проект на Java 17;
- подключить JUnit 5, AssertJ, Jackson и Allure;
- настроить Surefire и теги;
- добавить загрузку конфигурации.

### Этап 2. Управление процессом
- реализовать запуск JAR;
- реализовать независимое чтение stdout/stderr;
- реализовать таймауты и остановку процесса;
- проверить отсутствие зависаний и утечек дочернего процесса.

### Этап 3. MCP-клиент
- реализовать JSON-RPC request/response;
- реализовать request id;
- реализовать request, notify и callTool;
- реализовать базовый handshake;
- реализовать обработку tool error и JSON-RPC error.

### Этап 4. Протокольные тесты
- initialize;
- notifications/initialized;
- tools/list;
- состав и схемы 13 инструментов;
- неизвестный метод и негативные параметры;
- несколько последовательных запросов.

### Этап 5. Интеграционные тесты
- Jira read/search;
- Confluence read/search;
- создание тестовых объектов;
- обновление/переход/комментарий;
- очистка данных.

### Этап 6. Отчётность и CI
- Allure labels и attachments;
- Jenkins pipeline;
- публикация отчётов;
- проверка маскирования секретов.

## 15. Критерии готовности технической основы

- [ ] Проект собирается на Java 17.
- [ ] Путь к JAR задаётся конфигурацией.
- [ ] JAR запускается отдельным процессом.
- [ ] stdout и stderr читаются независимо.
- [ ] Протокольный обмен не загрязняется логами.
- [ ] Клиент сопоставляет ответы по request id.
- [ ] Уведомления не ожидают ответа.
- [ ] JSON-RPC error и MCP tool error различаются.
- [ ] Все ожидания ограничены таймаутами.
- [ ] Процесс гарантированно закрывается после тестов.
- [ ] Секреты маскируются в логах и Allure.
- [ ] Интеграционные данные изолированы и безопасно очищаются.
- [ ] Jenkins может запускать наборы по тегам и публиковать Allure.

## 16. Открытые решения перед написанием кода

1. Выбрать точную версию Allure и закрепить её в Maven.
2. Уточнить, как AQA job получает JAR: сборка основного репозитория в том же pipeline или скачивание артефакта.
3. Уточнить точные переменные конфигурации основного приложения и обязательные параметры запуска.
4. Зафиксировать используемый MCP handshake: классический initialize или современный discovery/stateless режим.
5. Сверить JSON Schema всех 13 инструментов и сохранить эталонные контракты.
6. Подготовить отдельные Jira project и Confluence space с известными правами и workflow.

Открытые решения не блокируют создание каркаса проекта и реализацию управления процессом. Они должны быть закрыты до написания зависящих от них интеграционных тестов.
