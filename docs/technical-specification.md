# Техническая спецификация AQA-фреймворка

## 1. Назначение

Документ описывает целевую архитектуру и технические требования внешнего AQA-проекта для Atlassian MCP Light.

AQA проверяет MCP-сервер как самостоятельное приложение через его публичный MCP-интерфейс. Тестовый проект не импортирует внутренние классы основного приложения, не подменяет его HTTP-клиент и не обращается напрямую к внутренним сервисам Jira или Confluence.

Основные принципы:

- black-box testing;
- неизменность STDIO-транспорта основного приложения;
- изоляция сборки, MCP-сервера и тестов в отдельных Docker-контейнерах;
- управление полным циклом через Jenkins;
- изоляция параллельных тестовых сессий;
- работа с выделенными тестовыми ресурсами Jira и Confluence;
- безопасное хранение секретов, учёт созданных тестовых данных и подготовка их к последующей очистке.

Документ описывает целевое состояние AQA-инфраструктуры. Наличие описанного компонента не означает, что он уже реализован. Фактический протокольный контракт уже проверен по исходникам основного приложения и зафиксирован отдельно в [mcp-contract.md](mcp-contract.md).

## 3. Общая архитектура

В системе используются три отдельных Docker-контейнера. Jenkins Pipeline управляет их запуском и передачей артефактов.

| Компонент | Назначение |
|---|---|
| Build container | Получает исходный код основного проекта и собирает исполняемый JAR |
| MCP Server container | Запускает STDIO Bridge и дочерние процессы MCP-сервера |
| AQA container | Запускает Maven, JUnit 5, MCP Client и формирует результаты тестирования |
| Jenkins | Управляет этапами сборки, запуском контейнеров, тестированием, публикацией отчётов и очисткой |

Последовательность работы:

1. Jenkins получает исходный код AQA-проекта и выбранную ревизию основного проекта.
2. Build container собирает основной проект и создаёт JAR.
3. JAR передаётся в MCP Server container через временный Docker volume или общий каталог Jenkins workspace.
4. MCP Server container запускает STDIO Bridge.
5. AQA container подключается к Bridge по внутренней Docker network.
6. Bridge запускает отдельный процесс MCP-сервера для каждого принятого клиентского соединения и проксирует потоки.
7. AQA выполняет тесты через MCP Client.
8. Jenkins публикует JUnit XML и Allure Report.
9. Jenkins останавливает контейнеры и удаляет временные ресурсы.

Docker network изолирована от внешней сети. Порт Bridge не публикуется на хост и доступен только AQA-контейнеру внутри этой сети.

## 4. STDIO Bridge

### 4.1. Назначение

STDIO Bridge обеспечивает связь между AQA-контейнером и MCP-сервером, который работает в отдельном контейнере.

MCP-сервер сохраняет исходный транспорт: JSON-RPC сообщения поступают в stdin процесса, ответы передаются через stdout, диагностические сообщения направляются в stderr.

AQA не запускает JAR через ProcessBuilder, поскольку процесс находится в другом контейнере. AQA подключается к TCP-порту Bridge. TCP используется только как внутренний канал передачи байтов между контейнерами; это не замена MCP STDIO на HTTP или другой MCP transport.

### 4.2. Модель соединения

Одно TCP-соединение AQA с Bridge соответствует одной изолированной MCP-сессии и одному дочернему процессу MCP-сервера.

Для каждого принятого соединения Bridge:

1. Создаёт дочерний процесс Java с запуском JAR.
2. Передаёт байты от TCP-соединения в stdin дочернего процесса.
3. Передаёт stdout дочернего процесса обратно в TCP-соединение.
4. Направляет stderr дочернего процесса в диагностический лог контейнера.
5. При закрытии TCP-соединения закрывает stdin дочернего процесса.
6. Ожидает штатного завершения процесса в пределах таймаута.
7. При необходимости принудительно завершает процесс и освобождает ресурсы.

Bridge не разбирает JSON-RPC и не изменяет содержимое сообщений. Он выполняет двунаправленную передачу потоков.

### 4.3. Требования к Bridge

- отдельный процесс Bridge запускается при старте MCP Server container;
- Bridge принимает соединения только во внутренней Docker network;
- каждое соединение получает отдельный процесс MCP-сервера;
- stdout и stderr дочернего процесса не смешиваются;
- ограничивается максимальное количество активных сессий;
- задаются таймаут запуска, завершения и бездействия;
- при аварийном отключении клиента дочерний процесс завершается;
- ошибки запуска и завершения процесса фиксируются в структурированных диагностических логах;
- для каждого соединения Bridge создаёт correlation ID; записи содержат событие, connection ID, PID дочернего процесса, причину завершения и exit code (если процесс завершился);
- диагностические записи направляются только в stderr/файл журнала Bridge и не попадают в TCP-поток MCP;
- Jenkins сохраняет журнал Bridge как артефакт прогона и обеспечивает корреляцию с тестовыми сессиями;
- секреты не выводятся в логи;
- Bridge не должен писать диагностические сообщения в поток, предназначенный для MCP-клиента.

Bridge реализуется как небольшой самостоятельный Java-компонент. Его код и сборка располагаются в каталоге docker/server/bridge. MCP SDK для проксирования не требуется.

### 4.4. Границы ответственности

Bridge отвечает за TCP-соединение, создание дочернего процесса, передачу stdin/stdout/stderr и диагностические события жизненного цикла.

MCP Client в AQA отвечает за TCP-соединение со стороны клиента, JSON-RPC, MCP handshake, идентификаторы запросов, таймауты ожидания ответа и проверку структуры сообщений. Он не управляет PID и потоками дочернего процесса напрямую.

Проверки поведения MCP выполняются по TCP/JSON-RPC. Подтверждение создания и завершения дочерних процессов выполняется по отдельному диагностическому журналу Bridge, который собирается Jenkins; диагностический канал не является частью MCP-протокола.

Bridge не должен содержать бизнес-логику Jira/Confluence и не должен знать назначение MCP-инструментов.

## 7. MCP Client и протокол

### 7.1. Транспортный обмен

AQA устанавливает TCP-соединение с Bridge и передаёт по нему исходный поток STDIO-сообщений.

Сообщения MCP/JSON-RPC передаются в формате UTF-8, по одному JSON-объекту на строку. Bridge не изменяет сообщения и не добавляет собственное framing.

Клиент должен:

- сериализовать JSON-RPC запросы;
- назначать уникальные request ID;
- записывать сообщения в TCP-соединение;
- читать ответы из соединения;
- сопоставлять ответы с запросами по ID;
- различать response, error и notification;
- ограничивать ожидание ответа таймаутом;
- корректно завершать соединение.

В первой версии один MCP Client отправляет запросы последовательно. Параллельность достигается отдельными сессиями и процессами, а не одновременной записью нескольких потоков в один канал.

### 7.2. Поддерживаемые режимы MCP

Фактическая реализация основного проекта проверена. Полный контракт с точными именами metadata, версиями, кодами ошибок и схемами инструментов описан в [mcp-contract.md](mcp-contract.md). Оба режима входят в обязательный объём AQA.

**Классический MCP lifecycle:**
- Поддерживаемые версии: `2024-11-05` и `2025-11-25`.
- `initialize` требует `protocolVersion`, объект `capabilities` и `clientInfo` с непустыми строковыми `name` и `version`.
- Сервер возвращает выбранную версию, `capabilities.tools` и `serverInfo`.
- Если передана другая непустая версия, сервер выбирает `2025-11-25`.
- После initialize клиент отправляет notification `notifications/initialized` без id.
- До READY методы `tools/list` и `tools/call` возвращают `-32001`; повторный initialize возвращает `-32600`.

**Stateless MCP режим:**
- Версия: `2026-07-28`.
- Поддерживаемые методы: `server/discover`, `tools/list`, `tools/call`.
- В каждом запросе в `params._meta` передаются `io.modelcontextprotocol/protocolVersion` и объект `io.modelcontextprotocol/clientCapabilities`; `io.modelcontextprotocol/clientInfo` необязателен.
- `server/discover` возвращает supportedVersions, capabilities, ttlMs=300000, cacheScope=public и serverInfo metadata.
- Успешные stateless-ответы содержат `resultType=complete` и `io.modelcontextprotocol/serverInfo` в result._meta.
- Stateless-запросы не требуют initialize и не изменяют состояние классического lifecycle.
- Неподдерживаемая версия возвращает `-32022`.

**Практические правила реализации клиента:**
1. Поддержать два явных режима клиента, не смешивать их в одном сценарии.
2. Для classic session выполнять initialize → notifications/initialized → tools/list/tools/call.
3. Для stateless session выполнять server/discover и затем stateless tools/list/tools/call без initialize.
4. В stateless metadata использовать точные ключи, приведённые в контракте.
5. Проверять как валидную, так и отсутствующую/неполную metadata.
6. Сверять список и схемы инструментов с ответом tools/list, а не только с локальными ожиданиями.

### 7.3. JSON-RPC и MCP-ошибки

Клиент и тесты должны различать:

- успешный JSON-RPC response с result;
- JSON-RPC error с объектом error;
- успешный JSON-RPC response, внутри result которого находится isError: true;
- notification, для которой ответ не ожидается.

Ошибка выполнения MCP-инструмента с isError: true не является JSON-RPC error.

Отдельно проверяются некорректный JSON, Invalid Request, неизвестный метод, неверные параметры протокола, неизвестный инструмент и ошибки выполнения инструмента.

**Jira:**

**Confluence:**

Схемы инструментов не следует дублировать вручную в нескольких местах тестового проекта. Фактический результат tools/list является источником текущего контракта; целевые ожидания и проверенные ограничения хранятся централизованно и обновляются вместе с изменениями основного проекта.

### 7.5. Таймауты и некорректные сообщения

Таймауты подключения, ожидания ответа и завершения сессии задаются конфигурацией.

Не использовать Thread.sleep как механизм синхронизации. Ожидание должно быть ограничено таймаутом и основано на фактическом чтении ответа, состоянии соединения или процесса.

Для негативных протокольных тестов предусмотреть отдельную отправку raw JSON line. Обычный типизированный API клиента не должен позволять случайно отправить некорректное сообщение.

## 8. Управление сессиями и параллельность

### 8.1. Изоляция

Одна MCP-сессия соответствует одному TCP-соединению с Bridge и одному дочернему процессу MCP-сервера.

Каждый параллельно выполняемый тестовый класс получает собственную сессию. Внутри одного класса методы выполняются последовательно и используют сессию этого класса, если сценарий не требует отдельного процесса.

Тесты, проверяющие запуск, аварийное завершение, некорректный обмен или восстановление соединения, создают отдельные изолированные сессии.

McpSessionManager учитывает активные сессии. JUnit extension создаёт class-scoped сессию в `beforeAll` и закрывает её в `afterAll`; методы класса выполняются последовательно. Тесты, которым требуется заведомо новое состояние процесса, открывают отдельную сессию в собственном lifecycle и закрывают её в `finally`/extension callback. Закрытие класса должно выполняться и при ошибке тестового метода. Bridge дополнительно завершает дочерний процесс при разрыве TCP-соединения, в том числе если AQA JVM аварийно завершилась.

### 8.2. JUnit 5

Начальная конфигурация:

- параллельное выполнение тестовых классов;
- последовательное выполнение методов внутри класса;
- начальное значение — 2 параллельных worker;
- возможность увеличить значение до 4 после проверки стабильности;
- число worker задаётся конфигурацией;
- отдельная сессия Bridge создаётся для каждого параллельного тестового класса.

Параллельное выполнение методов одного класса не включать по умолчанию: они могут использовать общий контекст и MCP-сессию.

### 8.3. Ограничения

- число параллельных сессий AQA не должно превышать лимит Bridge;
- Bridge ограничивает число дочерних процессов;
- каждый тест использует уникальные тестовые данные;
- один канал не используется несколькими потоками одновременно;
- при падении теста сессия должна закрываться через JUnit lifecycle;
- параллельность JUnit и Jenkins не увеличивается одновременно без оценки ресурсов и нагрузки на Atlassian.

В первой версии один Jenkins Pipeline запускает один AQA-прогон. Разделение Jira и Confluence на параллельные Jenkins branches возможно позднее, после стабилизации тестового уровня.

| CONFLUENCE_TEST_SPACE_KEY | Выделенный Confluence space |
| AQA_RUN_ID | Уникальный идентификатор прогона |

### Параметры основного MCP-сервера

Сервер получает собственные настройки через ENV. Для текущей версии используются:

| Переменная | Назначение |
|---|---|
| JIRA_URL | Базовый URL Jira |
| JIRA_EMAIL | Email пользователя Atlassian |
| JIRA_TOKEN | Atlassian API token |
| CONFLUENCE_URL | URL Confluence; при отсутствии используется JIRA_URL/wiki |
| MCP_MAX_TEXT_LENGTH | Ограничение длины текста в ответе |
| MCP_MAX_RESPONSE_BYTES | Ограничение размера HTTP-ответа |
| ATLASSIAN_LOG_LEVEL | Уровень логирования |

Параметры Jira обязательны для текущей конфигурации приложения, в том числе при проверках только Confluence.

AQA не получает токен Atlassian, если ему не требуется прямое обращение к Atlassian API. В штатном сценарии секреты нужны MCP Server container, а тесты работают через MCP-инструменты.

### Хранение секретов

- В Jenkins использовать Credentials.
- Передавать секреты MCP Server container во время запуска.
- Не хранить секреты в Git, Dockerfile и тестовых ресурсах.
- Не включать секреты в параметры командной строки.
- Не выводить токены, Authorization headers и полный environment dump в логи или Allure.
- Локально использовать переменные окружения или локальный .env, исключённый из Git.

## 10. Тестовые данные и очистка

### 10.1. Тестовое окружение

Для интеграционных тестов выделяются:

- отдельный Jira project;
- отдельный Confluence space;
- отдельная тестовая учётная запись с минимально необходимыми правами.

Тесты не должны изменять пользовательские объекты вне выделенного тестового пространства.

### 10.2. Уникальность данных

Каждый прогон получает AQA_RUN_ID. Для каждого теста генерируется собственный testId.

Имена и содержимое создаваемых объектов должны включать уникальный маркер прогона и теста, например:

**aqa-<runId>-<testId>**

Это предотвращает коллизии между повторными и параллельными запусками.

### 10.3. Учёт объектов и последующая очистка

Фактический MCP-контракт содержит 13 инструментов, но не содержит операций удаления Jira-задач или Confluence-страниц. Поэтому автоматическое удаление тестовых объектов не входит в первую версию AQA. Тесты не должны обходить MCP-интерфейс прямыми вызовами Atlassian REST API ради очистки.

TestDataManager регистрирует каждый объект сразу после успешного создания. Запись реестра содержит:
- тип объекта (Jira issue / Confluence page);
- ID и, если применимо, issue key или space key;
- `AQA_RUN_ID` и `testId`;
- время создания и тест-кейс, создавший объект.

Реестр сохраняется в отдельный файл/артефакт прогона и обновляется по мере создания объектов. Он должен сохраняться при успешном завершении, падении теста и ошибке cleanup/teardown. Jenkins архивирует реестр вместе с отчётами.

В первой версии teardown закрывает MCP-сессии и освобождает инфраструктурные ресурсы, но не удаляет Atlassian-объекты. Созданные данные остаются в выделенных тестовых Jira project и Confluence space и идентифицируются по маркерам. Их удаление выполняется вручную или отдельной административной процедурой вне AQA-прогона. Если позднее будет добавлен автоматический cleanup, он должен быть отдельным явно включаемым компонентом с allowlist тестовых проектов/пространств, проверкой принадлежности объекта и отдельными правами.

Тесты должны быть независимы от порядка выполнения. Для Jira workflow явно задаётся ожидаемое начальное состояние. Для Confluence обновление выполняется с учётом версии страницы.

## 11. Наборы тестов

JUnit tags:

| Тег | Назначение |
|---|---|
| smoke | Быстрая проверка доступности и основных функций |
| critical | Основные критичные сценарии |
| integration | Проверки с реальными Jira и Confluence |
| full | Полный набор тестов |

Уровни проверок:

| Уровень | Содержание |
|---|---|
| Protocol | JSON-RPC 2.0, классический handshake (2024-11-05/2025-11-25), stateless (2026-07-28), discovery, metadata, notifications, request ID, ошибки |
| Process | Доступность Bridge, запуск и завершение сессии, таймауты, отключение клиента |
| Tools | Наличие 13 инструментов и соответствие схем |
| Negative | Неверные параметры, неизвестные методы и инструменты, отсутствующие сущности |
| Integration | Реальные операции Jira и Confluence |
| E2E | Полные сценарии создания, чтения и изменения тестовых объектов с регистрацией их идентификаторов |

Performance/load testing не входит в первую версию. Проверки таймаутов, устойчивости соединения и ограничений сессий относятся к Process и Protocol.

## 12. Allure и диагностика

Для каждого теста указывать:

- стабильный ID тест-кейса;
- понятное имя и описание;
- функциональную область;
- тип проверки;
- шаги MCP-взаимодействия.

Вложения:

- JSON-RPC request;
- JSON-RPC response;
- сведения о сессии;
- диагностические записи Bridge по connection ID;
- состояние TCP-соединения;
- PID и exit code дочернего процесса из журнала Bridge, если доступны;
- ID созданных Jira/Confluence объектов;
- состояние и путь к сохранённому реестру созданных объектов;
- сведения об окружении без секретов.

Категории ошибок:

- Protocol;
- Process;
- Configuration;
- Jira;
- Confluence;
- Negative;
- Integration;
- Test Data.

Перед прикреплением данных выполняется маскирование токенов, паролей, Authorization headers и других чувствительных значений. Не прикладывать полный environment dump.

## 13. Docker-окружение

### Build container

- Использует JDK 17 и Maven Wrapper основного проекта.
- Получает исходный код выбранной ревизии основного проекта.
- Выполняет сборку Maven.
- Передаёт исполняемый JAR в общий временный volume или каталог Jenkins workspace.
- После сборки не остаётся постоянно работающим.

### MCP Server container

- Использует Java 17 runtime.
- Содержит JAR основного приложения и STDIO Bridge.
- Запускает Bridge как управляющий процесс.
- Bridge запускает дочерние процессы MCP-сервера по одному на клиентское соединение.
- Получает конфигурацию Jira/Confluence через ENV.
- Не публикует порт Bridge на хост.

### AQA container

- Использует JDK 17 и Maven.
- Содержит исходный код AQA-проекта.
- Подключается к Bridge по внутренней Docker network.
- Запускает выбранные JUnit-наборы.
- Сохраняет surefire-reports, Allure results, реестр созданных Atlassian-объектов и диагностические материалы в каталог, доступный Jenkins.

Контейнеры должны иметь ограниченные ресурсы и корректные health checks. Jenkins удаляет временные контейнеры, network и volume после завершения Pipeline, в том числе при ошибке тестов.

## 14. Jenkins Pipeline

Jenkins является единственным CI-оркестратором первой версии. GitHub Actions не используется.

Этапы Pipeline:

1. **Checkout** — получение исходников AQA и выбранной ревизии основного проекта.
2. **Build MCP** — сборка основного проекта в Build container.
3. **Build images** — подготовка MCP Server и AQA образов.
4. **Start MCP Server** — запуск контейнера Bridge и проверка его готовности.
5. **Run AQA** — запуск тестов в AQA container с выбранным набором и уровнем параллельности.
6. **Publish reports** — публикация JUnit XML и Allure Report.
7. **Collect diagnostics** — сохранение журналов Bridge и реестра созданных тестовых объектов.
8. **Cleanup** — остановка контейнеров, удаление временной Docker network и volume. Atlassian-объекты этим этапом не удаляются.

### Политика запуска

- При каждом коммите в AQA-проект — smoke.
- Перед слиянием изменений — critical.
- По расписанию — integration и full.
- Вручную — любой набор через параметр Pipeline.

Конкретные триггеры и правила перехода между этапами задаются в Jenkinsfile. Параметры запуска должны включать тестовый набор, ревизию основного проекта и уровень параллельности.

Для интеграционных прогонов Jenkins передаёт секреты через Credentials. Секреты не должны попадать в консольный вывод.

При падении тестов Pipeline всё равно публикует доступные отчёты и выполняет cleanup.

## 15. Maven и команды запуска

Основные команды тестового проекта:

- Сборка и запуск тестов: **./mvnw clean test**
- Smoke: **./mvnw test -Dgroups=smoke**
- Critical: **./mvnw test -Dgroups=critical**
- Integration: **./mvnw test -Dgroups=integration**
- Full: **./mvnw test -Dgroups=full**

Фактические параметры Maven Surefire должны быть согласованы с JUnit Platform и проверены на реальном запуске. Указанные команды являются целевым интерфейсом запуска.

AQA получает адрес Bridge и параметры тестового окружения через переменные окружения. Путь к JAR не передаётся в AQA container: JAR доступен только MCP Server container.

## 16. Порядок реализации

### Этап 1. Docker Build

- подготовить Build Dockerfile;
- получать выбранную ревизию основного проекта;
- собирать JAR;
- передавать артефакт в общий временный volume;
- проверять наличие и целостность артефакта.

### Этап 2. MCP Server и Bridge

- подготовить образ MCP Server container;
- реализовать TCP listener Bridge;
- реализовать запуск дочернего JAR на каждое соединение;
- реализовать двунаправленную передачу stdin/stdout;
- направлять stderr в логи;
- реализовать таймауты, лимит сессий и завершение процессов;
- проверить поведение при отключении клиента.

### Этап 3. AQA Client

- реализовать McpSession и McpClient;
- реализовать JSON-RPC request/response;
- реализовать request ID;
- реализовать последовательную отправку и чтение ответов;
- реализовать классический handshake;
- реализовать stateless metadata и методы server/discover, tools/list и tools/call;
- реализовать таймауты и закрытие сессии.

### Этап 4. Protocol и Process tests

- проверить подключение к Bridge;
- проверить запуск и завершение сессии;
- проверить classic initialize/notifications/initialized;
- проверить server/discover и stateless tools/list/tools/call с валидной и невалидной metadata;
- проверить tools/list и tools/call;
- проверить JSON-RPC errors и isError;
- проверить некорректные сообщения и таймауты;
- проверить отсутствие зависших дочерних процессов.

### Этап 5. Tools tests

- проверить наличие всех 13 инструментов;
- проверить схемы и обязательные параметры;
- проверить позитивные и негативные вызовы;
- проверить структуру результатов.

### Этап 6. Integration и E2E

- подготовить тестовый Jira project и Confluence space;
- реализовать TestDataFactory и TestDataManager;
- проверить операции Jira;
- проверить операции Confluence;
- реализовать регистрацию созданных объектов и сохранение реестра;
- проверить сохранение реестра при падении теста и при штатном завершении;
- добавить E2E-сценарии.

### Этап 7. Parallel execution

- включить параллельное выполнение классов;
- выдавать отдельную MCP-сессию каждому классу;
- начать с 2 worker;
- проверить стабильность и изоляцию данных;
- увеличить до 4 worker после успешной проверки.

### Этап 8. Jenkins и отчётность

- реализовать Jenkinsfile;
- собирать и запускать три Docker-контейнера;
- запускать наборы по тегам;
- публиковать JUnit XML и Allure;
- проверять маскирование секретов;
- проверять cleanup при успешном и аварийном завершении.

## 18. Технические проверки перед и во время реализации

Следующие пункты требуют проверки на фактическом коде и окружении; они не считаются заранее подтверждёнными:

1. Bridge должен корректно завершать дочерний процесс при закрытии TCP-соединения, аварии AQA-контейнера и остановке самого Bridge.
2. Последовательный цикл обработки STDIO в текущем MCP-сервере должен оставаться совместимым с выбранной моделью «одна сессия — один процесс».
3. Классический handshake и stateless-режим являются обязательными отдельными наборами. Контракт stateless-режима подтверждён в McpProtocol.java: версия 2026-07-28, discovery и per-request metadata.
4. Реальные лимиты параллельных соединений и таймауты необходимо подобрать по результатам прогонов.
5. Схемы всех 13 инструментов необходимо сверять с фактическим результатом tools/list, а не только с локальными копиями ожиданий.
6. Jenkins Pipeline должен сохранять отчёты и выполнять cleanup даже при ошибке на любом этапе.

## 19. Принятые архитектурные решения

Для первой версии зафиксированы:

- три Docker-контейнера: Build, MCP Server и AQA;
- Jenkins как CI-оркестратор;
- Java 17 и Maven;
- MCP STDIO основного приложения без изменения;
- отдельный TCP Bridge для связи между контейнерами;
- отдельный дочерний процесс MCP-сервера на каждое соединение Bridge;
- отдельная MCP-сессия для каждого параллельного тестового класса;
- параллельность JUnit 5 с начальным значением 2 worker;
- Jackson, JUnit 5, AssertJ, Allure и Maven Surefire;
- black-box проверки всех 13 инструментов;
- реальные интеграционные тесты Jira и Confluence;
- уникальные тестовые данные и сохранение реестра для последующей очистки;
- публикация JUnit XML и Allure Report через Jenkins.

Решения о реализации не должны нарушать эти границы ответственности. Изменение архитектуры допускается только после отдельного обоснования и обновления этой спецификации.
