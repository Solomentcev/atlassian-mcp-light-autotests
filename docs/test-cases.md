# Каталог тест-кейсов

Каталог содержит автоматизированные и запланированные black-box сценарии Atlassian MCP Light через публичный MCP/JSON-RPC контракт и STDIO. Для каждого сценария указаны предусловия, параметры, шаги и ожидаемый результат. В текущем коде 51 тестовый метод: 48 обычных `@Test` и 3 параметризованных метода по 3 набора данных каждый, всего 57 выполнений на один полный прогон. Из них 28 интеграционных методов связаны со стабильными ID каталога, 23 метода проверяют инфраструктуру AQA.

## Общие правила

- ID стабильны и не переиспользуются: `MCP-xxx`, `JIRA-xxx`, `CONF-xxx`, `PROC-xxx`, `DATA-xxx`, `REL-xxx`. Для новых тест-кейсов используются следующие свободные номера соответствующей группы.
- Приоритеты: P0 — критичный для базовой работоспособности; P1 — важная функциональность; P2 — дополнительный негативный/граничный сценарий.
- **Smoke suite** (`@Tag("smoke")`) — короткая проверка доступности STDIO/MCP и базового контракта: MCP-004, MCP-005, MCP-006, MCP-019, MCP-020, MCP-021 и MCP-036. MCP-021 выполняет безопасный read-вызов Confluence и поэтому требует доступного тестового Atlassian-окружения.
- **Regression suite** (`@Tag("regression")`) — полный набор автоматизированных проверок; smoke-тесты входят в него. Метка назначается на уровне каждого тестового класса, поэтому новые тесты в этих классах автоматически попадают в regression. Дополнительная метка `smoke` назначается только перечисленным методам.
- Запуск smoke: `mvn -Pintegration,smoke clean test`; запуск regression: `mvn -Pintegration,regression clean test`. Без профиля `integration` интеграционные классы отключены через `AQA_RUN_INTEGRATION`; выполняются unit-тесты.
- Типы: Protocol, Process, Integration, Negative, E2E.
- Все тестовые данные должны создаваться в выделенном тестовом окружении.
- **Allure:** самостоятельные действия (запуск процесса/сессии, handshake, отправка сообщения, вызов инструмента) оформляются осмысленными шагами. Проверки выполняются в тестовом коде через универсальные AssertJ-совместимые методы `AllureAssertions`; каждая проверка получает отдельный Allure step и понятное описание `.as()`.
- Шаг должен описывать действие или конкретное проверяемое условие, а не технический getter/setter или построение DTO. Не дублировать один и тот же шаг вложенными `Allure.step` и `@Step`.
- В тест-кейсах ниже «валидный запрос» означает запрос, соответствующий фактической JSON Schema инструмента и контракту MCP-сервера.
- Ожидаемые поля и ограничения приведены в [фактическом MCP-контракте](mcp-contract.md); при выполнении теста схема дополнительно сверяется с текущим ответом `tools/list`.



### Статус автоматизации

Статус показывает наличие автоматизированного теста, связанного с ID через Allure `@Story` и JUnit tag `case-<ID>`. Он **не означает**, что тест прошёл на каждом окружении или что соответствующий Docker/Jenkins сценарий проверен end-to-end.

- **Автоматизировано** — в текущем коде есть тест с соответствующим ID.
- **Запланировано** — сценарий описан, но связанного автоматизированного теста в текущей ветке нет.

23 unit-теста инфраструктуры AQA подробно перечислены после каталога с параметрами, шагами и ожидаемыми результатами. Они покрывают компоненты тестового фреймворка, но не подменяют PROC/JIRA/CONF end-to-end кейсы. На текущий момент реальные Jira/Confluence CRUD-сценарии и полный Docker runtime не автоматизированы.

## 8. Внешние предусловия интеграционного окружения

Эти условия относятся к настройке тестового Atlassian tenant, а не к архитектурным решениям AQA. Они должны быть выполнены до запуска Jira/Confluence integration-набора.

1. **Jira project.** Используется отдельный тестовый project, ключ задаётся через `JIRA_TEST_PROJECT_KEY`. Проект должен позволять создать issue только с параметрами публичного MCP-контракта: `project_key`, `summary`, `description` и необязательный `issue_type`. Дополнительные обязательные custom fields недопустимы, поскольку MCP-инструмент их не принимает. Должен быть доступен тип `Bug`, используемый по умолчанию.
2. **Jira workflow.** Для позитивного перехода должна существовать задача в исходном статусе и доступный переход, имя которого однозначно определяется передаваемым фрагментом. Для негативного сценария используется заведомо недоступный фрагмент перехода. Фактические имена/статусы хранятся в конфигурации тестового окружения, а не зашиваются в контракт MCP.
3. **JQL/CQL.** Запросы строятся вокруг выделенного project/space и уникального маркера `AQA_RUN_ID + testId`. Базовые шаблоны: JQL — `project = <JIRA_TEST_PROJECT_KEY> AND summary ~ "<marker>"`; CQL — `space = "<CONFLUENCE_TEST_SPACE_KEY>" AND title ~ "<marker>"`. Для пустой выдачи используется уникальный marker, который не создаётся ни одним тестом. Вызовы search не передают offset/cursor; пагинация Atlassian API остаётся внутренней.
4. **Права Jira.** Основная учётная запись имеет Browse Projects, Create Issues, Transition Issues и Add Comments для тестового project; чтение проекта и пользователя также доступно. Для негативных сценариев используются отдельные учётные записи/настройки без Browse Projects и без Add Comments. Если конкретную комбинацию прав нельзя изолировать в tenant, соответствующий негативный кейс помечается как environment-blocked, а не считается пройденным.
5. **Права Confluence.** Основная учётная запись имеет View, Create и Edit для выделенного space. Для сценария пустого списка/недоступного пространства используется отдельная учётная запись без доступа к пространствам; запуск этого сценария допустим только при подтверждённом отсутствии доступных spaces.
6. **Ресурсы и очистка.** Ключи project/space и идентификаторы тестовых пользователей задаются конфигурацией окружения. Созданные Jira issues и Confluence pages регистрируются в JSONL event log. В MCP-контракте нет delete tools: первая версия не удаляет Atlassian-объекты и не обходит MCP через REST API. После прогона администратор выполняет отдельную ручную/административную очистку только по выгруженному реестру и allowlist выделенных project/space.

JSON Schema и annotations всех 13 инструментов сверяются с фактическим ответом `tools/list` при каждом обновлении основного проекта и в контрактном наборе AQA. Формат JSONL event log, crash recovery, `WRITE_INTENT/WRITE_CONFIRMED/UNKNOWN_OUTCOME` и запрет автоматического retry определены в [технической спецификации AQA](technical-specification.md).

| `McpClientTest` | Request/response ID, notifications, classic handshake и stateless metadata |
| `McpProcessSessionTest` | Classic/stateless session lifecycle и закрытие процесса |
| `AllureDiagnosticsTest` | Маскирование Authorization и секретных переменных, сохранение обычной диагностики |
